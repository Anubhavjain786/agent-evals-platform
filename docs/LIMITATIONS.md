# Known limits

What the platform does not do (yet), where its numbers can mislead, and what
would fix each item. Ordered roughly by how much they matter.

## Statistical validity

| Limit                                                                                                                                       | Why it matters                                                                         | Mitigation today / next step                                                                                                                                                                                                                                                                                     |
| ------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Small suites detect only large effects.** With 12 tasks the minimum detectable pass-rate difference is typically 25–40 pp.                | A real 10 pp improvement will usually read "no detectable difference".                 | The report states the detectable effect next to every non-significant verdict. Next: more tasks (the unit of analysis), not more trials; a power calculator in the "new experiment" form.                                                                                                                        |
| **Results generalise only to tasks like the suite's.**                                                                                      | A config that wins on 12 hand-written tasks may lose on your real traffic.             | Tags and the per-task heatmap show where a win comes from. Next: import tasks from production transcripts; stratified reports per tag.                                                                                                                                                                           |
| **LLM-judge scores carry judge bias and variance.**                                                                                         | Judges favour verbosity and their own model family; scores drift if the judge changes. | Judges are used sparingly, always next to deterministic checks, at temperature 0, with a different model family from the candidates, and the judge model is fixed per deployment. Next: record the judge model per score in reports, repeat-judging to measure judge variance, and human-label calibration sets. |
| **Only one comparison family per report.** Every config is compared with the baseline (Holm-corrected); there are no all-pairs comparisons. | With 3+ configs you cannot directly read B vs C.                                       | Re-run with a different baseline, or open two experiments. Next: optional all-pairs with correction.                                                                                                                                                                                                             |
| **Excluding infrastructure errors can bias results** if errors correlate with a config (e.g. one model is throttled more on hard tasks).    | The surviving runs of that config are a non-random sample.                             | Errors are counted per config in the report, flagged in warnings, and "Retry failed runs" re-runs them. Next: report the result with errors counted as failures as a sensitivity check.                                                                                                                          |
| **Timeouts count as failures** even when the provider, not the agent, was slow.                                                             | Provider latency spikes can look like agent failures.                                  | Runs are interleaved so latency spikes hit all configs; the run budget gives Hermes a wrap-up notice before the hard kill. Next: separate model latency from agent time using per-call timings.                                                                                                                  |
| **Fixed α = 0.05, no sequential testing.** Peeking at a running experiment and stopping early inflates false positives.                     | The UI shows provisional results live.                                                 | Provisional results are labelled as such. Next: always-valid (sequential) confidence intervals.                                                                                                                                                                                                                  |

## Isolation and security

| Limit                                            | Detail                                                                                                                                                                                                                                                                                     | Next step                                                                                                                                                         |
| ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Runs share one container.**                    | Each run has its own `HERMES_HOME`, workspace, runtime dir, write sandbox (`HERMES_WRITE_SAFE_ROOT`) and minimal environment, but the terminal tool runs shell commands as the same OS user. A malicious or confused agent could read another run's workspace or interfere with processes. | Hermes' own Docker terminal backend (`terminal.backend: docker`) per config, or a `RemoteHermesRunner` that runs each attempt in a throwaway container / microVM. |
| **The agent can read its own provider key.**     | The key is passed through the environment; a shell command can print it. Other secrets (judge key, unrelated env vars) are withheld.                                                                                                                                                       | Use scoped, low-limit keys for eval runs, or a key-injecting egress proxy.                                                                                        |
| **Tasks and scorer commands are trusted code.**  | `command` scorers run shell commands from the suite definition; UI-created suites can include them.                                                                                                                                                                                        | Fine for an internal tool with code review. For untrusted authors: run scorers in the same per-run sandbox, or disallow `command` for UI-created suites.          |
| **No authentication or authorisation.**          | Anyone who can reach the port can start experiments (and spend tokens).                                                                                                                                                                                                                    | Put it behind SSO/a reverse proxy; add API keys and roles.                                                                                                        |
| **`--yolo` disables Hermes' command approvals.** | Required for unattended runs.                                                                                                                                                                                                                                                              | Same as the first row: stronger sandboxing per run.                                                                                                               |

## Hermes integration

| Limit                                                                                       | Detail                                                                                                                                                                                                                                                 |
| ------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Pinned to the Hermes CLI contract (v0.22.1).**                                            | Stream events and usage fields are parsed defensively (unknown events ignored, missing fields default), but a breaking CLI change needs an adapter update. The image tag is pinned for reproducibility.                                                |
| **Single-turn tasks only.**                                                                 | One prompt, then the agent works autonomously. No simulated user replying mid-task, no multi-session scenarios (e.g. "learn in session 1, use in session 2"). Memory is evaluated by _seeding_ it, which tests use of memory, not formation of memory. |
| **~5–10 s of Hermes start-up per run**, and cold starts are serialised by the startup gate. | Throughput on a 4-vCPU machine is roughly 4–6 runs/minute for short tasks; slow models dominate beyond that.                                                                                                                                           |
| **Hermes' own cost estimate is unavailable for custom endpoints.**                          | The config's pricing table fills in; without one, cost is shown as unknown.                                                                                                                                                                            |
| **Web/browser toolsets are not exercised by the sample suites.**                            | They work if the container has network access and the relevant keys, but make results less reproducible.                                                                                                                                               |

## Product and operations

| Limit                                                                                                 | Detail                                                                                                                                                              |
| ----------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Single node.**                                                                                      | SQLite and the in-process scheduler/event bus assume one API instance. The seams for Postgres, a broker and remote runners are described in DESIGN §11.             |
| **No dataset versioning beyond content hashes.**                                                      | Experiments freeze definition snapshots and hashes, but there is no diffing of suite versions in the UI.                                                            |
| **Run artifacts grow with use.**                                                                      | Workspaces are kept for inspection (Hermes homes are deleted after each run). There is no retention policy yet; deleting an experiment removes its run directories. |
| **No cost guardrails.**                                                                               | Nothing stops a 10,000-run experiment. Next: a pre-flight cost estimate and a per-experiment budget that stops the queue.                                           |
| **The suite editor is a YAML textarea.**                                                              | Validated live against the shared schema, but no structured form or fixture upload; fixtures must be added to `evals/fixtures` on disk.                             |
| **The UI is not localised** and was checked at desktop and narrow widths, not exhaustively on mobile. |
