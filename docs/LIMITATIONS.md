# Known limits

This page lists what the platform does not do yet, where its numbers can be
misleading, and what would fix each problem. The most important ones come
first.

## Statistics

| Limit                                                                                                                                                       | Why it matters                                                                                         | What helps today / next step                                                                                                                                                                                                                                         |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Small suites only notice big differences.** With 12 tasks, the smallest difference we can reliably notice is usually 15–40 points.                        | A real 10-point improvement will often show as "no detectable difference".                             | The report always shows the smallest detectable difference next to such a result. Next: add more tasks (more tasks help more than more tries), and show a "how many tasks do I need?" helper in the form.                                                            |
| **Results only apply to tasks like the ones in the suite.**                                                                                                 | A config that wins on 12 hand-written tasks might lose on real user requests.                          | Tags and the per-task table show where a win comes from. Next: create tasks from real production conversations, and show results per tag.                                                                                                                            |
| **The LLM judge has its own bias and randomness.**                                                                                                          | Judges tend to like long answers and models from their own family. Scores change if the judge changes. | The judge is used rarely, always together with rule-based checks, with temperature 0, from a different model family, and fixed per deployment. Next: store the judge model with each score, judge twice to measure its randomness, and compare it with human labels. |
| **Each config is only compared with the baseline.**                                                                                                         | With 3 or more configs, you cannot directly read "B vs C".                                             | Run again with a different baseline, or create a second experiment. Next: optional "everyone vs everyone" comparisons.                                                                                                                                               |
| **Leaving out provider errors can bias results** if errors happen more for one config (for example, one model is rate-limited more on hard tasks).          | The remaining runs of that config are no longer a fair sample.                                         | Errors are counted per config, shown as a warning, and "Retry failed runs" runs them again. Next: also show the result with errors counted as failures, as a check.                                                                                                  |
| **Timeouts count as failures**, even when the provider (not the agent) was slow.                                                                            | A slow provider can look like a weak agent.                                                            | Runs are mixed in order, so slow periods hit all configs. Hermes gets a "please finish up" warning before the hard stop. Next: separate model waiting time from agent time.                                                                                          |
| **Fixed 0.05 threshold and no "early stopping" rules.** Looking at a running experiment and stopping as soon as it looks good makes false wins more likely. | The UI shows results live while the experiment runs.                                                   | Live results are clearly marked as "provisional". Next: statistics that stay valid even when you check early.                                                                                                                                                        |

## Isolation and security

| Limit                                             | Details                                                                                                                                                                                                                                | Next step                                                                                                                                       |
| ------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| **All runs share one container.**                 | Each run has its own Hermes setup, folder, write limit and minimal environment. But the terminal tool runs shell commands as the same system user. A bad or confused agent could read another run's folder or disturb other processes. | Use Hermes' own Docker terminal option (`terminal.backend: docker`) per config, or a runner that starts each run in a throwaway container.      |
| **The agent can read its own API key.**           | The key is passed as an environment variable, so a shell command could print it. Other secrets (like the judge key) are not passed.                                                                                                    | Use separate keys with low limits for evals, or a proxy that adds the key outside the container.                                                |
| **Tasks and check commands are trusted code.**    | `command` checks run shell commands from the suite file. Suites created in the UI can include them too.                                                                                                                                | Fine for an internal tool with code review. For untrusted authors: run checks inside the run's sandbox, or block `command` checks in UI suites. |
| **No login or permissions.**                      | Anyone who can reach the port can start experiments (and spend tokens).                                                                                                                                                                | Put it behind company login or a reverse proxy; add API keys and roles.                                                                         |
| **`--yolo` turns off Hermes' command approvals.** | This is needed because nobody is there to approve commands during a run.                                                                                                                                                               | Same as the first row: stronger isolation per run.                                                                                              |

## Hermes integration

| Limit                                                                           | Details                                                                                                                                                                                                                                        |
| ------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Built for Hermes' command-line output (v0.22.1).**                            | The output is read carefully (unknown lines are ignored, missing fields get defaults), but a big change in Hermes' output would need a code update. The Docker image version is fixed so results can be repeated.                              |
| **One-message tasks only.**                                                     | One prompt, then the agent works alone. No simulated user replying during the task, and no "learn in session 1, use it in session 2" tests. Memory is tested by giving the agent starting notes, so we test _using_ memory, not _creating_ it. |
| **Each run needs 5–10 s for Hermes to start**, and starts happen one at a time. | On a 4-CPU machine this gives about 4–6 short runs per minute. With slow models, the model is the bottleneck.                                                                                                                                  |
| **Hermes cannot price custom endpoints itself.**                                | The prices in the config are used instead. Without them, cost shows as "unknown".                                                                                                                                                              |
| **The sample suites do not test web or browser tools.**                         | They work if the container has network access and the needed keys, but results become less repeatable.                                                                                                                                         |

## Product and operations

| Limit                                                                                           | Details                                                                                                                                                                    |
| ----------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Runs on one machine only.**                                                                   | SQLite and the in-process queue and live updates assume one API server. How to grow beyond that is described in DESIGN §11.                                                |
| **Simple versioning.**                                                                          | Experiments save frozen copies and hashes of tasks and configs, but the UI cannot show the difference between two versions of a suite.                                     |
| **Run files keep growing.**                                                                     | Run folders are kept so you can inspect them (the Hermes setup is deleted after each run). There is no automatic clean-up yet; deleting an experiment removes its folders. |
| **No spending limits.**                                                                         | Nothing stops someone from starting a 10,000-run experiment. Next: show an estimated cost before starting, and a budget that stops the queue.                              |
| **The suite editor is a plain YAML text box.**                                                  | It checks your YAML live against the rules, but there is no form and no file upload. Starting files must be added to `evals/fixtures` on disk.                             |
| **The UI is English only**, and was checked on desktop and narrow screens, not fully on phones. |                                                                                                                                                                            |
